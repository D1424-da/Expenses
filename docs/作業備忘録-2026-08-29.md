## 4. どう直すか（未実施・運営者の判断待ち）

**除外がレシピ系を意図的に捨てる判断だったのかどうかで、直し方が変わる。**

### A. 意図的ではなかった場合

1. **集約先17本を検索対象に戻す**——統合で本文を集めた結果がここにあり、
   301も canonical もここを向いている。いまサイトで最も薄くない記事群
2. **残している18本のうち薄いものを外す**——3,000字前後のものは、
   除外した記事と見分けがつかない
3. **1と2を同時に、1回で行う**——別々にやると、どちらが効いたか分からなくなる

戻すときは `scripts/apply_search_exclude.py` でフラグと meta robots を同期し、
`build_blog.py` を実行する（一覧・カテゴリ・サイトマップに戻す）。
`HIGH_PRIORITY_SLUGS` の見直しも同じ回で行う。

### B. 意図的だった場合（レシート家計簿に絞る方針）

**301 の行き先を、残す18本のほうへ付け替える。** いまのままだと、統合で
集めた評価がどこにも届かない。付け替えは `scripts/merge_articles.py` を
使う（手作業でやると6か所のどれかを必ず忘れる、と `CLAUDE.md` にあるとおり）。

## 6. ホスティングの適否

「Netlify / Cloudflare Pages / Vercel に移すべきか」を検討した。**移さない。**

| いま | 評価 |
|---|---|
| **Firebase Hosting**（フロント） | **そのままで最適** |
| **Render 無料**（OCR API） | 既知の制約あり・対処済み |

### Firebase Hosting を動かす理由が無い

- Authentication と Firestore を同じ Firebase で使っており、**統合されている
  利点のほうが大きい**
- 静的サイトなので、Next.js の互換性（Vercel を選ぶ最大の理由）が関係ない
- `firebase.json` に CSP・セキュリティヘッダー・キャッシュ制御・`.html` を
  正規形とする301の整理が積み上がっている。**これを他社に移植し直す作業に
  見合う利点が無い**

移行はURL・リダイレクト・sitemap を触ることになる。**インデックスの問題を
抱えている最中に、配信基盤を動かすべきではない。**

### Render のコールドスタートは対処済み

`render.yaml` は `plan: free` で、15分アイドルでスリープする。ただし
`static/app.js` の `prewarmOcr()` がアプリ起動時に `/api/health` を叩くので、
**画面を開いた時点で起動が始まる**（`CLAUDE.md`「GitHub Actions は
ジョブ1回につき最低1分課金される」の節。keep-alive を止めた経緯もそこ）。

残る取りこぼしは「開いた直後に即撮影する人」だけ。**費用をかけて有料プランに
する前に、その頻度を測るほうが先。**
