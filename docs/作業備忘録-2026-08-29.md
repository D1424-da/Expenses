## 4. どう直すか（未実施・運営者の判断待ち）

**除外がレシピ系を意図的に捨てる判断だったのかどうかで、直し方が変わる。**

### A. 意図的ではなかった場合

1. **集約先17本を検索対象に戻す**——統合で本文を集めた結果がここにあり、
   301も canonical もここを向いている。いまサイトで最も薄くない記事群
2. **残している18本のうち薄いものを外す**——3,000字前後のものは、
   除外した記事と見分けがつかない
3. **1と2を同時に、1回で行う**——別々にやると、どちらが効いたか分からなくなる

戻すときは `scripts/apply_search_exclude.py` でフラグと meta robots を同期し、
`build_blog.py` を実行する（一覧・カテゴリ・サイトマップに戻す）。
`HIGH_PRIORITY_SLUGS` の見直しも同じ回で行う。

### B. 意図的だった場合（レシート家計簿に絞る方針）

**301 の行き先を、残す18本のほうへ付け替える。** いまのままだと、統合で
集めた評価がどこにも届かない。付け替えは `scripts/merge_articles.py` を
使う（手作業でやると6か所のどれかを必ず忘れる、と `CLAUDE.md` にあるとおり）。

### 決めたこと（2026-09-02）

**除外は意図的だった**（レシート家計簿を核キーワードにする方針。運営者に確認）。
よって **B**——ただし「301 の行き先を残す18本へ付け替える」は**やらない**。
301元はレシピ・献立の記事で、レシート系へ向けると話題が食い違い、関連のない
リダイレクトとして評価が引き継がれない（ソフト404扱い）。レシピ記事どうしで
集約されている今の形が正しい。

代わりに**内部リンクを引いた**（PR #355・46ファイル）。除外76本は `noindex, follow`
なので、Google は今もそこから出るリンクを辿る。「検索結果には出ないが、リンクは
配れる」資産だったのに、**76本のうち60本が検索対象18本へのリンクを1本も持って
いなかった**。しかも束の中心にあるはずの `receipt-kakeibo-basics` が他の7本へ
1本もリンクしていなかった。

| | 前 | 後 |
|---|---|---|
| 検索対象18本へのリンクが1本も無い除外記事 | 60 / 76 | **0 / 76** |
| `receipt-kakeibo-basics` が受けるリンク | 2本 | **19本** |
| `receipt-kakeibo-basics` が出すリンク | 0本 | **7本** |

設計は **76本 → 中心（receipt-kakeibo-basics）→ 深掘り7本**。全記事から全記事へ
引くと同じ文言が並ぶテンプレートになり、量産と判断された経緯を繰り返す。
文面は46本すべて書き分け、行き先は話題で選んだ（家計簿・レシート寄り → レシート
系、レシピ・献立寄り → 献立系）。記事の frontmatter・`articles.json`・`sitemap.xml`
は触っていない。

**効果の見方:** 8/25 の noindex 化と合わせて数週間。Search Console のインデックス数
（8月時点で約100ページ中14）と、レシート系7本の表示回数。**結果を見るまで次の手は
打たない。**

## 6. ホスティングの適否

「Netlify / Cloudflare Pages / Vercel に移すべきか」を検討した。**移さない。**

| いま | 評価 |
|---|---|
| **Firebase Hosting**（フロント） | **そのままで最適** |
| **Render 無料**（OCR API） | 既知の制約あり・対処済み |

### Firebase Hosting を動かす理由が無い

- Authentication と Firestore を同じ Firebase で使っており、**統合されている
  利点のほうが大きい**
- 静的サイトなので、Next.js の互換性（Vercel を選ぶ最大の理由）が関係ない
- `firebase.json` に CSP・セキュリティヘッダー・キャッシュ制御・`.html` を
  正規形とする301の整理が積み上がっている。**これを他社に移植し直す作業に
  見合う利点が無い**

移行はURL・リダイレクト・sitemap を触ることになる。**インデックスの問題を
抱えている最中に、配信基盤を動かすべきではない。**

### Render のコールドスタートは対処済み

`render.yaml` は `plan: free` で、15分アイドルでスリープする。ただし
`static/app.js` の `prewarmOcr()` がアプリ起動時に `/api/health` を叩くので、
**画面を開いた時点で起動が始まる**（`CLAUDE.md`「GitHub Actions は
ジョブ1回につき最低1分課金される」の節。keep-alive を止めた経緯もそこ）。

残る取りこぼしは「開いた直後に即撮影する人」だけ。**費用をかけて有料プランに
する前に、その頻度を測るほうが先。**

## 7. 検証と訂正（同日・追記）

上の内容を実測で検証した。**数字はすべて一致した。ただし4章の前提が誤っている。**

### 7-1. 数字は合っている

| 主張 | 実測 |
|---|---|
| 全141記事 = 統合47 + 除外76 + 残り18 | 一致 |
| フラグと `meta robots` が76本すべて一致 | 141件検査して不一致0 |
| サイトマップ25件 = トップ+一覧+カテゴリ5+記事18 | 一致 |
| 47本のうち45本の行き先が `searchExclude` | 一致（例外は `kakeibo-app-compare` の2本のみ） |
| 残した18本が均質な帯に収まる | 17本が 3,028〜4,987字、`kakeibo-app-compare` のみ約8,900字 |
| noindex の集約先が最も厚い | 14,556 / 13,963 / 13,644 / 13,313 / 11,018字… |

文字数は数え方で数百字ずれるが分布の形は同じ。**表に無い `fridge-ai-recipe`
（13,313字・統合3本）も noindex で、4番目に厚い。**

### 7-2. 訂正：除外は「話題」で選んでいない

4章は「除外の判断が『レシート・アプリ系を残し、レシピ・献立系を外す』という
**話題**で行われたため、結果として厚さでは逆の選別になった」と推測している。
**これは誤り。**選定基準は `f9ed0cf`（2026-08-25・運営者承認済み）に明記されている。

> 残した17本: 実装を根拠に書いた新方針の記事7本 / インデックス済みの
> 公開記事6本 / クリック実績のある記事 / サイト内で最も順位が高い記事。

基準は話題でも厚さでもなく、**Google に受け入れられた証拠があるかどうか**
（インデックス済み・クリック実績・順位）と、**核キーワードの新方針記事**の
2つだった。同コミットの状況説明もそれを裏づけている——インデックス済みが
18→14に減り、クロール済み・未登録が84件、検出のみ・未クロールが49件。
**サイト単位で低く評価されている状態への対処**であって、記事個々の厚さを
見た選別ではない。

厚い集約先が noindex 側に集まっているのは、選別を誤ったからではなく、
**それらに受け入れの証拠が無かったから**である。

### 7-3. したがって 4-A・4-B はどちらも採れない

**4-A（集約先17本を戻す）** は、8/25 の判断そのものを、**実施4日後・測定前に
巻き戻す**ことになる。`CLAUDE.md` の「効果が出ないからといって施策を
重ねないこと」は、逆向き（戻す方向）にも同じく効く。除外の再クロールと
再評価には数週間かかると4章自身が書いている。

**4-A の手順2（残した18本のうち薄いものを外す）** はさらに危うい。薄い側の
実体は次のとおりで、8本中7本が **2026-08-24 に核キーワード「レシート家計簿」
で書いた新方針の記事**である。

```
3,962 receipt-kakeibo-excel      3,620 receipt-scan-vs-photo
3,728 receipt-ocr-accuracy       3,525 kakeibo-receipt-security
3,662 long-receipt-ocr           3,459 weekly-kondate-shopping ← これだけ旧
3,636 receipt-ocr-how-it-works   3,028 denshi-receipt-kakeibo
```

`docs/記事設計-レシート家計簿.md` が競合指数ほぼゼロの61語を狙って設計した
本体で、公開から5日しか経っていない。文字数だけで切ると**設計を自分で
取り消す**ことになる。薄さが問題なら、外すのではなく厚くするほうが整合する。

**4-B（301の行き先を残す18本へ付け替える）** も採らない。統合は主題の
近さで集約先を決めており、行き先を「インデックスされている記事」に
付け替えると、内容の関係が無いページへ301を向けることになる。

### 7-4. いまの状態は設計どおりで、可逆である

「301 の行き先が noindex では受け取る側がいない」は現象としては正しいが、
**事故ではない。**`f9ed0cf` は明記している。

> 記事HTMLは削除していない。直接URLで読めるし、フラグを戻せば元に戻る。

統合（厚くする）と除外（母数を絞る）は目的の違う別々の施策で、後者が
前者を一時的に覆っている状態。**戻す判断をする段階で、この17本が
最初の候補になる**——サイトで最も厚く、45本ぶんの301が既にここを向いている。
その意味で、この棚卸しの価値は「いま直すべき欠陥を見つけたこと」ではなく、
**「母数を作り直すときに、どこから戻せばよいかが分かったこと」**にある。

### 7-5. 測定との関係

4章5節は「2・3は施策の追加ではなく実行漏れなので、効果測定を待つ対象とは
別に扱ってよい」としている。**意図の話としては筋が通るが、測定の話としては
成立しない。**

2026-08-28 に未定義URLの404化をデプロイしており、これは**インデックス数の
推移で判定する**設計になっている。ここで17本を検索対象に戻すと、
インデックス数は404化の効果と無関係に最大17増え、切り分けができなくなる。

いま動かす場合は、404化の効果をインデックス数ではなく直接見える指標
（存在しないURLが404を返すことは 8/28 に確認済み、「検出 - インデックス
未登録」の減少、クロール統計）で評価し、**戻した17本のURLを記録して
おく**こと。Search Console は URL 単位で状態を追えるので、増分を分けて
読める。混ざるのは総数だけになる。

### 7-6. 結論

**いま入れる変更は無い。**待つ対象が2つ（8/25の除外・8/28の404化）あり、
どちらも効果が出るまで数週間かかる。判定は 9月中旬。

その判定で「変わらない」と出たときに、**noindex を一部戻して母数を
作り直す**——その戻す先が、7-4 のとおりこの17本である。本棚卸しは
その準備として読むのが正しい。
